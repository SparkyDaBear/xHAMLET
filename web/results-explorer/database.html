xHAMLET result catalog

Database guide

This guide describes the SQL catalog created by scripts/sync_result_database.py. The public results explorer reads a static JSON snapshot; it does not expose the database or accept SQL from a browser.

The default catalog is a local SQLite file. PostgreSQL is supported when a shared, multi-user database is needed. RAW, mzML, and FASTA binary contents remain outside either database.

Connect and Refresh

Local SQLite

The default command writes xhamlet-results.sqlite3 in the current directory.

python scripts/sync_result_database.py \
  --config configs/config.yaml \
  --static-snap

sqlite3 xhamlet-results.sqlite3

Shared PostgreSQL

Supply a PostgreSQL URL for a shared catalog. Keep credentials out of the static site.

python scripts/sync_result_database.py \
  --config configs/config.yaml \
  --database-url 'postgresql://USER:PASSWORD@HOST:5432/xhamlet' \
  --static-snap

To regenerate only the public JSON snapshot from an already-populated database, without scanning pipeline outputs, run python scripts/sync_result_database.py --snapshot-only --static-snap.

Data Model

Each PXD has a current pipeline run. A run owns its source RAW roster, captured output artifacts, LLM extraction, ReLink search runs, mzIdentML document summaries, and compact cross-link observations.

project
  +-- pipeline_run
       +-- llm_output -- llm_response
       +-- output_artifact
       +-- source_file
       +-- search_run
            +-- mzid_document
                 +-- crosslink_match

source_file identifies an original RAW filename and its file-clustering assignment. crosslink_match is a compact, passing paired-peptide observation tied to an mzIdentML document, source spectrum, and resolved RAW file where possible.

SQL Recipes

Replace named parameters with your client syntax. The SQLite CLI supports .parameter set :pxd PXD042173; most Python and PostgreSQL clients bind parameters directly.

All catalog records for one PXD

SELECT p.accession, p.title, run.processed_at, run.accepted,
       run.stage_status
FROM project AS p
JOIN pipeline_run AS run USING (project_id)
WHERE p.accession = :pxd;

RAW files and clustering assignments for one PXD

SELECT source.filename, source.assignment_json
FROM project AS p
JOIN pipeline_run AS run USING (project_id)
JOIN source_file AS source USING (pipeline_run_id)
WHERE p.accession = :pxd
ORDER BY source.filename;

All target-mapped cross-links for one PXD

SELECT p.accession, search.taxid, match.source_file, match.scan_number,
       match.alpha_sequence, match.beta_sequence,
       match.alpha_proteins, match.beta_proteins, match.xi_score
FROM project AS p
JOIN pipeline_run AS run USING (project_id)
JOIN search_run AS search USING (pipeline_run_id)
JOIN mzid_document AS document USING (search_run_id)
JOIN crosslink_match AS match USING (mzid_document_id)
WHERE p.accession = :pxd
  AND match.pass_threshold
  AND json_array_length(match.alpha_proteins) > 0
  AND json_array_length(match.beta_proteins) > 0
ORDER BY match.xi_score DESC;

For PostgreSQL, use jsonb_array_length instead of json_array_length.

All records related to a protein accession

SQLite:

SELECT p.accession, search.taxid, match.source_file, match.scan_number,
       match.alpha_sequence, match.beta_sequence, match.xi_score
FROM project AS p
JOIN pipeline_run AS run USING (project_id)
JOIN search_run AS search USING (pipeline_run_id)
JOIN mzid_document AS document USING (search_run_id)
JOIN crosslink_match AS match USING (mzid_document_id)
WHERE match.pass_threshold
  AND (
    EXISTS (SELECT 1 FROM json_each(match.alpha_proteins)
            WHERE value = :protein_accession)
    OR EXISTS (SELECT 1 FROM json_each(match.beta_proteins)
               WHERE value = :protein_accession)
  )
ORDER BY p.accession, match.xi_score DESC;

PostgreSQL replaces the JSON predicates with match.alpha_proteins ? :protein_accession OR match.beta_proteins ? :protein_accession.

Find compact rows requiring mapping QC

SELECT p.accession, match.source_file, match.scan_number,
       match.alpha_sequence, match.beta_sequence,
       match.alpha_proteins, match.beta_proteins, match.xi_score
FROM project AS p
JOIN pipeline_run AS run USING (project_id)
JOIN search_run AS search USING (pipeline_run_id)
JOIN mzid_document AS document USING (search_run_id)
JOIN crosslink_match AS match USING (mzid_document_id)
WHERE match.pass_threshold
  AND (json_array_length(match.alpha_proteins) = 0
       OR json_array_length(match.beta_proteins) = 0)
ORDER BY p.accession, match.xi_score DESC;

Search LLM-extracted metadata

SELECT p.accession, response.field_key, response.value_json,
       response.accession_json, response.confidence
FROM project AS p
JOIN pipeline_run AS run USING (project_id)
JOIN llm_output AS output USING (pipeline_run_id)
JOIN llm_response AS response USING (llm_output_id)
WHERE response.field_key = 'comment[cross-linker]'
ORDER BY p.accession;

Quality and Scope

The catalog only exports projects whose pipeline run is marked accepted. The static snapshot additionally omits a compact cross-link when either peptide has no target protein mapping. This suppresses target-decoy or unresolved pairings from the public table while retaining the original compact rows in the SQL database for QC.

Large artifacts are not embedded in the local database. Their relative path, type, byte size, modified time, and SHA-256 remain cataloged; the configurable local inline-content limit determines whether text/JSON content is retained.

Normalized mzIdentML Roadmap

The current catalog intentionally stores compact cross-link observations rather than every mzIdentML entity. The detailed schema proposal adds normalized spectra_data, search_database, db_sequence, peptide, peptide_modification, peptide_evidence, spectrum_result, spectrum_item, item_evidence, CV/user parameter, and protein-inference tables.

Those Phase 2 tables are design documentation, not currently populated by the synchronizer. Use crosslink_match for today's result exploration and retain the original mzIdentML artifacts for full source-level analysis.

For the complete design rationale and the planned normalized schema, see DATABASE_SCHEMA.md in the repository.
